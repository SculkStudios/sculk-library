Sculk 6 is rebuilt milestone by milestone, so the most useful contributions right now are bug
reports against the architecture documents, research corrections and work on the current
milestone. The full guide is [`CONTRIBUTING.md`](https://github.com/SculkStudios/sculk-library/blob/dev/CONTRIBUTING.md).

## In short

1. Read `ARCHITECTURE.md`, `MODULES.md` and `THREADING.md`. Open an issue before a large change; a
   change that crosses module boundaries or adds public API needs agreement first, and a new
   architectural decision needs an ADR.
2. Branch from `dev`. Sculk 6 work never goes to `main`, which carries 5.x until 6.0 replaces it.
3. For a bug, add a failing test first. Keep a change to one concern.
4. `./gradlew build` must pass: ktlint, the tests on Java 21 and 25, the ABI check, the
   architecture rules and the bytecode gate.
5. If the public surface changed, run `./gradlew updateKotlinAbi` and commit the dump with the
   change.
6. If the change touches a server, run `./gradlew :integration-tests:boot:verifyBoot` and, where it
   applies, add an integration scenario.

Commits follow Conventional Commits (`feat(core): ...`, `fix(paper): ...`, `docs: ...`), in plain
English, one logical change each. Report security issues privately as described in
[`SECURITY.md`](https://github.com/SculkStudios/sculk-library/blob/dev/SECURITY.md), never in a public issue.

## This site

The site lives in `docs/` and is built with Astro Starlight and Bun:

```sh
cd docs
bun install --frozen-lockfile
bun run dev    # local preview
bun run build  # what CI builds
```

The roadmap page is generated from `MODULES.md` at build time. Code examples on these pages are
written against the current API; the compiled-snippet pipeline described in `DOCS_ARCHITECTURE.md`,
which will import examples from compiled sources instead, is planned for milestone M6.
