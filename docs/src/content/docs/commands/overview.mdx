```kotlin
override fun setup() {
    // command { } builds the command; the leading + registers it with the plugin.
    +command("kit") {
        description = "Claim a kit."
        permission = "myplugin.kit"
        aliases = listOf("kits")

        choice("kit", options = { kits.names() })
        cooldown(Duration.ofMinutes(5))

        player {
            val name: String = argument("kit")
            kits.give(player!!, name)
            reply("<value>Claimed <k>.</value>", "k" to name)
        }
    }
}
```

## The leading `+`

`command("kit") { … }` **builds** a command and hands it back as a `CommandSpec`. It does not
register anything on its own. The `+` in front is what gives it to the plugin:

```kotlin
val spec = command("kit") { … }   // built, not registered — nothing happens in game
+spec                             // now the server has it
```

They are separate so a spec can be built anywhere — in a test with no server, in a helper, or in a
list assembled from config at runtime — and only registered where a plugin exists to own it. Use
`commands(a, b, c)` to register several at once, and `declaredCommands` to read back what was
registered.

Declare commands anywhere in `setup()` — the order does not matter.

## Spec first, Brigadier second

`command { }` produces a **`CommandSpec`**: an immutable data class with no Brigadier and no Bukkit
types in its shape. One adapter turns it into Paper's command tree.

That split is why usage strings, permission filtering and `/help` are all testable with no server:

```kotlin
val spec = command("kit") { sub("give") { player("target"); executes { } } }

spec.usageAt("kit give")     // "/kit give <target>"
spec.flatten()               // every executable leaf with its full path
```

## Senders

```kotlin
player { /* players only */ }
console { /* console and command blocks only */ }
executes { /* anyone */ }
```

A node may declare **both** `player` and `console`, and each sender reaches its own:

```kotlin
+command("seen") {
    player { reply("<value>You are online.</value>") }
    console { reply("Run this in game to see yourself.") }
}
```

## Arguments

Resolved by name, so inserting one does not shift every later read:

```kotlin
+command("give") {
    player("target")
    material("item")
    int("amount", min = 1, max = 64)
    string("reason", optional = true)

    executes {
        val target: Player = argument("target")
        val amount: Int = argument("amount")
        val reason: String? = argumentOrNull("reason")
    }
}
```

| | |
| --- | --- |
| `string` `greedy` | a word, or the rest of the line |
| `int` `long` `double` | with optional `min`/`max` |
| `boolean` | |
| `player` `world` `material` | resolved for you |
| `uuid` `duration` | |
| `enum(name, MyEnum::class.java)` | matched case-insensitively |
| `choice(name) { … }` | one of a set |
| `argument(name, parser)` | your own |

An optional argument makes the preceding node executable. A required one cannot follow an optional
one — that is rejected when the spec is built.

## Suggestions that do not go stale

`choice` takes a **lambda**, not a list:

```kotlin
choice("kit", options = { kits.names() })
```

A snapshot captured at registration stops matching the moment a config reload changes the set, and
tab-completion then stays wrong until the next restart. The lambda is resolved per keystroke.

## Subcommands

```kotlin
+command("guild") {
    permission = "myplugin.guild"

    sub("create") {
        string("name")
        player { … }
    }
    sub("disband") {
        permission = "myplugin.guild.admin"
        player { … }
    }
}
```

A child inherits its parent's permission unless it declares its own.

## Missing arguments

A sender who omits a required argument gets the **usage line** — `/kit give <target> <kit>` — rather
than Brigadier's red caret, which says where parsing stopped but never what was wanted.

## Cooldowns

```kotlin
cooldown(Duration.ofSeconds(30))
```

Per sender, per command path. The check and the record are one atomic operation, so two commands
sent in the same tick cannot both pass.

## Middleware

Runs before the executor; returning false aborts. It is responsible for saying why, since only it
knows:

```kotlin
middleware { context ->
    if (arena.isRunning) {
        context.reply("<danger>Not during a match.</danger>")
        false
    } else {
        true
    }
}
```

## Suspending

Handlers are `suspend`, launched in the plugin scope:

```kotlin
player {
    val profile = repository.find(player!!.uniqueId).getOrNull()
    reply("<value><n></value> wins.", "n" to (profile?.wins ?: 0).toString())
}
```

## Generated help

`/help` is built from the same specs Brigadier was given and filtered by the same permissions, so
what a player sees cannot drift from what the server accepts. Turn it off with:

```kotlin
override val builtInHelp = false
```

## Framework messages

Every string the framework emits is overridable — no-permission, on-cooldown, bad-usage, and the
rest — via `CommandText`, so a fully localised plugin does not still say
"This command can only be used by players." in English.
