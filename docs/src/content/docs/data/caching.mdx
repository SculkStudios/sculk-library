---
title: Caching
description: Caffeine-backed in-memory cache over repositories — cache hits never touch the database.
---

For data read far more often than it is written — player profiles, economy balances, settings —
wrapping a repository with `SculkCache` removes the repeated round-trips. Hits are pure in-memory
reads backed by [Caffeine](https://github.com/ben-manes/caffeine).

## Creating a cache

`cached` is an extension on the repository:

```kotlin
val repo = sculk.data.repository<PlayerData, UUID>()

val cache = repo.cached(
    idOf = PlayerData::uuid,
    maximumSize = 10_000,
    expireAfter = Duration.ofMinutes(10),
    negativeExpireAfter = Duration.ofSeconds(30),
)
```

`idOf` is required and has no default: the cache cannot read an entity's key without reflection, and
asking for it is one line at the call site.

| Parameter | Default | Description |
| :--- | :--- | :--- |
| `idOf` | — | Reads an entity's primary key |
| `maximumSize` | `10_000` | Entries held before eviction |
| `expireAfter` | 10 minutes | How long after a write an entry survives |
| `negativeExpireAfter` | 30 seconds | How long a *known-absent* id is remembered |

### Negative caching

Absent ids are remembered too, briefly. A join handler asks for a profile, the player is new, nothing
is found — without a negative entry every later lookup that session asks the database the same
question and gets the same nothing, making a new player the *worst* case rather than the cheapest.

The negative TTL is deliberately short, so a row created by another server becomes visible in seconds
rather than on restart.

## Using the cache

`SculkCache` is **not** a `SculkRepository`. It exposes the subset that can be cached coherently:

```kotlin
sculk.scope.launchAsync {
    val result = cache.find(player.uniqueId)   // hit → no DB call
    cache.save(updatedData)                    // writes through to the DB and updates the entry
    cache.delete(player.uniqueId)              // deletes the row and marks the id absent
    val now = cache.peek(player.uniqueId)      // whatever is cached right now, no DB call, no suspend
}
```

For anything else — `query`, `count`, `findAll`, `topBy`, `saveAll`, `deleteWhere` — go to the
repository directly. Those either cannot be answered from a cache or would return a stale answer,
so the cache does not pretend to offer them.

## Cache miss behaviour

```
find(uuid)
  ├─ present?      → return the cached value
  ├─ known absent? → return null without a DB call
  └─ otherwise     → repo.find(uuid) → record present or absent → return
```

## Manual invalidation

If something writes to the database behind the cache's back — a console command, an external tool,
direct SQL — drop the affected entry:

```kotlin
cache.forget(uuid)   // one entry, positive and negative
cache.clear()        // everything, e.g. after a bulk import
```

`cache.size` reports the estimated number of cached entities.

## Recommended pattern: load on join, forget on quit

```kotlin
sculk.events.listen<PlayerJoinEvent> { event ->
    val player = event.player
    sculk.scope.launchAsync {
        cache.findOrCreate(player.uniqueId) { PlayerData(uuid = it) }
    }
}

sculk.events.listen<PlayerQuitEvent> { event ->
    val player = event.player
    sculk.scope.launchAsync {
        cache.peek(player.uniqueId)?.let { cache.save(it) }
        cache.forget(player.uniqueId)
    }
}
```

`peek` rather than `find` on quit: the player's data is in the cache if it is anywhere, and a miss on
quit means there is nothing to flush — not that the database should be asked again.

## findOrCreate

Gets a cached entity by id, or creates, persists and caches a new one if none exists:

```kotlin
sculk.scope.launchAsync {
    val result = healthCache.findOrCreate(player.uniqueId) { uuid ->
        PlayerHealth(uuid = uuid, hearts = 10, maxHearts = 10)
    }
    // result.value is always non-null here — either loaded or freshly created
}
```

The factory runs **only if no record exists** in either the cache or the database. The new entity is
saved and cached before the result returns.

## topBy

Lives on the repository, not the cache — a leaderboard read through a cache would be stale:

```kotlin
sculk.scope.launchAsync {
    val topShards = repo.topBy("shards", rows = 10).getOrThrow()
    val bottomHearts = repo.topBy("hearts", rows = 5, ascending = true).getOrThrow()
}
```

:::note
`topBy` sorts and limits **in SQL**, so it stays cheap on a table with a million rows. The previous
cache-side version loaded the whole table and sorted it in memory, which is survivable at a thousand
rows and not at a million.
:::

## Batch saves

`saveAll` upserts a list in one transaction; on failure the whole batch rolls back. It is a
repository method, so update the cache yourself if the entities are cached:

```kotlin
sculk.scope.launchAsync {
    val updated = onlinePlayers.map { getUpdatedData(it) }
    repo.saveAll(updated)
        .onSuccess { updated.forEach { cache.forget(it.uuid) } }
        .onFailure { message, _ -> logger.warning("Batch save failed: $message") }
}
```

## Best practices

- **One cache per entity type** — create it at startup and share it everywhere.
- **Use `findOrCreate` on join** — it removes the exists-check and guarantees a valid entity.
- **Use `topBy` on the repository for leaderboards** — always fresh, and the database does the sorting.
- **Use `saveAll` for bulk shutdown flushes** — one transaction beats N saves.
- **Size `maximumSize` off max-players** — for a 100-player server, a few hundred is plenty for
  player-scoped data.
- **Keep `expireAfter` short for externally-mutable data**; longer is fine for data only your plugin writes.
- **Go through the cache on hot paths** — bypassing it defeats the purpose and causes stale reads.
