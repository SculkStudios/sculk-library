`sculk-dialogs` (package `studio.sculk.dialog`) covers the whole dialog screen: a title, text, form
inputs and buttons. Answers arrive on the player's own thread.

```kotlin title="build.gradle.kts"
dependencies {
    implementation("studio.sculk:sculk-dialogs:6.0.0-SNAPSHOT")
}
```

## A form

```kotlin
import studio.sculk.dialog.Dialogs
import studio.sculk.dialog.dialog

val setup = dialog("<primary>Shop setup") {
    body("Fill in your shop.")
    val name = text("name", "Name", maxLength = 24)
    val open = toggle("open", "Open now")
    val price = number("price", "Price", 1f..100f, step = 1f, initial = 10f)
    val colour = choice("colour", "Colour", listOf("red" to "Red", "blue" to "Blue"), initial = "red")
    button("Save") { answer ->
        shops.save(answer.player, answer[name], answer[open] == true, answer[price], answer[colour])
    }
    button("Cancel")
    fallback { player -> player.sendMessage(Component.text("Use /shop setup <name> <price> instead.")) }
}

val dialogs = Dialogs(this)
dialogs.show(player, setup)
```

- Titles, body paragraphs, labels and option labels are templates rendered with the `Text` you
  give `Dialogs`, so theme styles work in them. Values such as a price or a player's name go in as
  placeholders, never into the template: `dialogs.show(player, spec, mapOf("price" to price))` fills
  `<price>` wherever the dialog uses it.
- One button makes a notice, two a confirmation (Escape presses the second), more a list of
  actions. A button without a handler only closes the dialog.
- Each input function returns the input, and `answer[input]` reads its answer with the input's
  own type: a text is a `String?`, a toggle a `Boolean?`, an amount a `BigDecimal?`. The string form,
  `answer.text("name")`, reads the same values by key.
- Answers run on the player's thread: the main thread on Paper, the player's region thread on
  Folia and Canvas. `show` may be called from any thread.

## Amounts

A slider suits a small range. For prices and balances, `amount` gives a text field that takes what
players type, `250`, `1.5k` or `2m`, and reads it back exactly as a `BigDecimal`:

```kotlin
val sell = dialog("<primary>Sell") {
    amount("price", "Price", min = BigDecimal.ONE, max = BigDecimal("1000000"), initial = BigDecimal("10000"))
    button("Sell") { answer -> answer.amount("price")?.let { listings.add(answer.player, it) } }
}
```

The field starts with the initial value written compactly (`10k`); `answer.amount("price")` is null
for text that is not an amount or falls outside the range. The suffixes are those of
[compact numbers](/guides/text/#compact-numbers), and an `Amounts` of your own can replace them.

## Answers are checked

A client may send anything back, so every getter checks the value against the input's
declaration: text longer than `maxLength`, a number or amount outside the range, an option id that
was not offered or a value of the wrong kind reads as `null`. Asking for an input the dialog does not have
is a programming error and throws.

## Registered dialogs

A dialog can also be part of the server's data, registered while the server starts, so the client
can offer it on the pause screen or behind its quick actions key. Register it from a
`PluginBootstrap` (a `paper-plugin.yml` with a `bootstrapper`), keeping the spec where the plugin
can reach it too:

```kotlin
object Forms {
    val rules: Key = Key.key("myplugin", "rules")
    val rulesDialog = dialog("<primary>Server rules") {
        body("Be kind. No griefing.")
        button("Agree") { answer -> answer.player.sendMessage(Component.text("Thanks!")) }
        button("Leave")
    }
}

class MyBootstrap : PluginBootstrap {
    override fun bootstrap(context: BootstrapContext) {
        context.registerDialog(Forms.rules, Forms.rulesDialog, setOf(DialogPlacement.PAUSE_SCREEN))
    }
}

// later, in the plugin:
dialogs.show(player, Forms.rules)
```

A registered dialog is the same for every player, so its templates are rendered once, without
placeholders. Its buttons run as soon as the plugin has made a `Dialogs`, with answers checked and
delivered on the player's thread as for any other dialog, whether the player opened it from the
pause screen or the plugin showed it. On a server without dialogs `registerDialog` returns an
`UnsupportedCapability` failure.

## Older servers

Dialogs arrived in Minecraft 1.21.6, so they work on every supported version except the oldest:
Paper 1.21.11 and every 26.x release have them, 1.21.4 does not. There (`dialogs.isAvailable` is
false) a dialog shows its `fallback` instead, on the player's thread. A dialog without one makes
`show` return an `UnsupportedCapability` failure: what a form should become without dialogs, a chat
prompt, a [menu](/guides/menus/) or nothing, is a decision only your plugin can make.

<Aside>
  Sculk's `integration-tests/dialogs` suite shows a form to a real client on every supported Paper
  version, Folia and Canvas, answers it with valid and invalid values, does the same for a dialog
  registered at bootstrap and offered on the pause screen, and checks the fallback on 1.21.4.
</Aside>
